# Проверка перед передачей

## Команды

Из корня проекта, с Python 3.10+:

```bash
python -m unittest discover -s tests_psb -v
python -m compileall -q psb scripts solution.py
node --check psb/static/chat.js
python -m psb.launcher --check
```

Для Linux/macOS при необходимости замените `python` на `python3`. Node.js применяется только для синтаксической проверки JS. Рабочее веб-приложение не зависит от Node.js.

На Windows дополнительно:

```powershell
.\START_PSB.cmd --check
.\START_PSB.cmd --port 8090 --no-browser
```

Вторую команду остановите Ctrl+C после проверки `/api/health` и главной страницы. Windows CI запускает настоящий CMD из другой папки, в каталоге с пробелами и кириллицей, с автоматическим поиском Python и с `PSB_PYTHON`.

## Что проверяет автоматизация

| Набор | Сценарии |
|---|---|
| Корпус | Граница редакций, период до начала, пересечения, уникальность ID, положение, фильтр документов |
| Генерация и проверка | Выдуманный источник, ложная цитата, неподтверждённый вывод, пустой отказ, некорректный результат проверки |
| Дата и контекст | Дата из текста и истории, конфликт дат, длинная история, недопустимая роль, независимость кейсов |
| API модели | Настоящие HTTP-запросы к локальному синтетическому API, одна модель для двух этапов, авторизация, запрет редиректа, очистка ошибок |
| HTTP | Главная, здоровье, источники, лимит тела, плохой запрос, Host/Origin, недопустимый путь |
| Запуск и настройки | `.env` как данные, кавычки/BOM, приоритет окружения, отсутствие утечки ключа, свободный порт, запуск дочернего процесса |
| JSONL | Ошибочная и слишком длинная строка не влияют на следующий кейс |
| Windows | Настоящий `START_PSB.cmd`, пути с пробелами/кириллицей, выбранный Python и понятная ошибка при его отсутствии |
| Браузер | Основной сценарий, дата, источник, темы, JSON-выгрузка, ошибка даты, отмена ожидания и новый диалог, мобильная ширина |
| Docker | Сборка образа, запуск Compose, успешная проверка здоровья, остановка |

В Linux две Windows-проверки пропускаются намеренно. Они должны пройти в отдельном Windows job. Сравнивайте не только итоговый статус, но и причины пропуска, если добавляете проверки.

## Ручной приёмочный сценарий

1. Распакуйте проект в новую папку с пробелами в имени и запустите CMD двойным щелчком.
2. Проверьте, что отображаются учебный режим, 3 документа и отсутствие подключённой модели.
3. Найдите документы для согласования; откройте положение и полный текст; закройте окно клавишей Escape.
4. Проверьте срок на 2026-03-01 и 2026-07-01: в разных редакциях должны быть соответственно пять и три рабочих дня.
5. Противоречащие друг другу дата вопроса и поле даты должны вызвать понятное сообщение; вопрос должен остаться в поле ввода.
6. Скачайте результат; проверьте дату, корпус, источники и отсутствие секретов в JSON.
7. Начните новый диалог: старые сообщения должны исчезнуть. Проверьте тему и ширину экрана телефона.
8. Если включена модель, проверьте сообщения об ошибке API и отсутствие непроверенных юридических выводов.
9. Остановите сервер Ctrl+C, повторно запустите и проверьте освобождение порта. Запустите два экземпляра: второй должен выбрать другой адрес.

## Границы результата

Успешный CI подтверждает воспроизводимость программных сценариев на учебных данных и тестовом API. Он не измеряет Recall@k на предоставленном корпусе, юридическую правильность, устойчивость ко всем атакам, производственную нагрузку или скор LLM-судьи. Эти проверки требуют материалов организаторов и настоящей модели; план находится в [HANDOFF.md](HANDOFF.md).
